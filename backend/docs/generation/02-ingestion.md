# 収集ジョブ（RSS取得→本文取得→LLMメタデータ抽出→重複判定→キャッシュ保存）

**想定パス**: `/backend/cmd/ingest`

**改訂(2026-08-29)**：ユーザーからのレビューを受け、以下3点を全面的に変更した設計に更新する。旧版（bigram Jaccard類似度による重複判定、フィード決め打ちタグ、1200文字への機械的な切り詰め）は本ドキュメントの内容で置き換える。

1. タグ判定・記事の要約(省略版)をLLMの**構造化出力(structured output)**で取得する
2. 重複判定を文字列類似度アルゴリズムからLLMベースの判定に変更する
3. 本文の文字数切り詰めをやめ、長い記事のみLLMに要約(省略版)も生成させる

## 概要
[01-feed-config.md](01-feed-config.md)の`article.json`に定義された全フィードを巡回し、新着記事を取得・LLMでメタデータ抽出・LLMで重複判定した上でPostgreSQLの`articles`テーブル（[04-schema.md](04-schema.md)）にキャッシュする。ユーザーからのリクエストとは完全に非同期・独立に動く。

## 実行タイミング・並行実行の防止（変更なし）
`cmd/ingest`は既存の`backend/scripts/batch-cron.sh`とは別のcronエントリとして定期実行する（目安10〜15分間隔）。単一プロセス・単一goroutineで逐次処理し、PostgreSQLのadvisory lockで多重起動を防止する（既存実装のまま）。

## フロー

### 1. フィード一覧の構築
[01-feed-config.md](01-feed-config.md)の`article.json`から`enabled: true`のフィードを読み込み、`Feed{ID, URL, Origin, Title}`の一覧を作る。この時点では外部通信は発生しない（ローカルファイル読み込みのみ）。

### 2. 各フィードのRSS取得
各フィードの`url`にGETし、XMLをパースして`<item>`（`title` / `link` / `pubDate`）の一覧を得る（既存の`internal/ingest.ParseRSS`をそのまま流用、RSS 2.0・RDF両対応は変更なし）。1フィードあたり直近N件（目安20件）まで。

**鮮度フィルタ**：`pubDate`が14日より古い記事はここで除外する（変更なし）。

### 3. 新着判定・完全一致URLの扱い（変更なし）
`articles.source_url`に既存レコードがある場合は本文再取得をスキップし、フィードのタグを既存レコードにマージする処理は**廃止**する（タグはフィード決め打ちではなくLLM判定になったため、この概念自体が無くなる。完全一致URLは単純にスキップでよい）。

### 4. 本文取得（変更なし）
新着URLのみ、jina.ai Readerで本文を取得する（`JINA_AI_API_KEY`未設定時はモックで、モック記事はキャッシュしない、極端に短い本文は除外——いずれも既存のまま）。

### 5. LLM構造化出力によるメタデータ抽出（新規）
本文取得に成功した記事ごとに、LLMへ**構造化出力(structured output)**でメタデータ抽出を1回依頼する（記事1件につきLLM呼び出し1回。記事本文が長くても、この呼び出しは他記事の内容と混ぜない＝N対1のような大きなプロンプトにはしない）。

**依頼するJSON Schema（案）**：
```json
{
  "shortenedTitle": "string, 45文字以内。UI表示用の短いタイトル",
  "tags": ["string", "..."],
  "author": "string または null。抽出できなければnull",
  "publishedAt": "string(ISO8601) または null。本文中から確認できればRSSのpubDateより優先、確認できなければnull（nullの場合はRSSのpubDateを使う）",
  "abbreviatedBody": "string または null。本文が2500文字を超える場合のみ、要約した本文をここに入れる。2500文字以下の場合はnull（元の本文をそのまま使うため）"
}
```
- `tags`は[01-feed-config.md](01-feed-config.md)で定めたフロントエンド固定タグ一覧に対する`enum`配列として、プロバイダの構造化出力機能で制約する（自由記述にしない）
- `abbreviatedBody`は**元の本文が2500文字を超える場合のみLLMに生成させる**。2500文字以下の記事は`abbreviatedBody: null`を期待し、常に元の本文をそのまま後段（重要度に関わる判定・台本生成プロンプト）で使う。これにより、以前のような「本文長に関わらず一律1200文字に切り詰め、記事によっては本文が実質ゼロになる」問題を避けつつ、極端に長い記事（数万文字）でプロンプトが肥大化するのも防ぐ
- 対応プロバイダ：Ollama Cloudでは構造化出力に強いモデル（Gemma系等、要検証）を使う想定。Gemini・OpenRouterも各々の構造化出力機能（`responseSchema`／`response_format: json_schema`等）に対応させる。プロバイダごとの対応状況は実装時に確認すること
- 本文取得自体（jina.ai）とメタデータ抽出（LLM）は別の呼び出し。ナビゲーションリンク除去（`stripNavigationLines`）はLLMに渡す前処理として引き続き行う

### 6. LLMベースの重複判定（アルゴリズム変更）
**旧方式（文字bigram Jaccard類似度、閾値0.35）は廃止する。** 理由：短い日本語見出しでは、意味的に無関係でも文字の重なりだけで高スコアになる／逆に本当に同じ話題でも文字の重なりが少なく低スコアになる、という既知の限界があり、Codexとのレビューでも「Phase 4での改善候補」と位置付けていたものを今回前倒しで解消する。

**新方式**：1回のingest実行につき、重複判定用のLLM呼び出しを**1回だけ**行う（記事ごとではなくバッチ処理）。

- **入力**：
  - 今回の実行で新規取得した記事の「元タイトル」一覧（`shortenedTitle`ではなく、記事本来のタイトル。省略版タイトルは表示用に情報が削られている可能性があり、同一性判定には不向きなため）
  - 既存キャッシュのうち直近14日以内・代表記事(`is_primary=true`)の「タイトル一覧＋既存`topic_group_id`」（新着記事が過去の既存グループに合流するケースを拾うため）
- **出力（構造化出力）**：新規記事タイトルそれぞれについて、以下のいずれかを返させる
  - 既存の`topic_group_id`（そのグループに合流）
  - 今回のバッチ内の他の新規タイトルと同じ内容（バッチ内でのグルーピング。新しい`topic_group_id`を1つ発行して両方に割り当てる）
  - どれとも一致しない（新しい`topic_group_id`を発行）
- 新規記事数が多くタイトル一覧が大きくなりすぎる場合の分割（バッチを複数回のLLM呼び出しに分ける等）は実装時の裁量とする

### 7. 代表記事(`is_primary`)の決定・タグの合算（一部変更）
同一`topic_group_id`内で本文が最も長い記事を代表記事とする（変更なし）。タグはグループ内の全記事（各記事がLLMで個別に判定したタグ）を合算し、代表記事の`tags`に反映する（フィード決め打ちのタグ合算ロジックは無くなったが、記事ごとにLLM判定したタグを合算する、という概念自体は残る）。

### 8. 保存
`articles`テーブルへupsert。スキーマの変更点は[04-schema.md](04-schema.md)参照（`importance_score`列は廃止、`shortened_title`・`author`列を追加）。

## 出力
生成パイプライン（[03-selection.md](03-selection.md)）が参照する`articles`テーブルの行。実行ごとのログ出力（フィード別取得件数・成功失敗数）は既存のまま維持する。

## その他の運用ルール（変更なし）
Firecrawlフォールバック未実装、言語判定なし、canonical URL正規化なし、フィード選定時の利用規約確認、極端に短い本文の除外——いずれも従来の方針を維持する。
