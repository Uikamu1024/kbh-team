# 収集ジョブ（RSS取得→本文取得→タグ付け→重複判定→キャッシュ保存）

**想定パス**: `/backend/cmd/ingest`（新規CLI、`cmd/gentrace`と同様のスタンドアロン実行形式）

## 概要
[01-feed-config.md](01-feed-config.md)の`article.json`に定義された全フィードを巡回し、新着記事を取得・正規化・重複判定した上でPostgreSQLの`articles`テーブル（[04-schema.md](04-schema.md)）にキャッシュする。ユーザーからのリクエストとは完全に非同期・独立に動く。

## 実行タイミング・並行実行の防止
既存の`backend/scripts/batch-cron.sh`（`POST /api/batch/run`を5分おきに叩く）とは**別のcronエントリ**として、`cmd/ingest`を定期実行する。目安は10〜15分間隔（RSSの更新頻度・jina.aiのレート制限を考慮）。生成バッチ（`batch/run`）より収集の方が独立して回ってよいので、同一cron/スクリプトに混ぜる必要はない。

**`cmd/ingest`は常に単一プロセス・単一goroutineで、フィード→記事を完全に逐次処理する**（並行fetch・並行DB書き込みは行わない）。理由：
- 手順6（重複判定）は「新しい記事1件 vs 既存キャッシュ全体」の比較を前提にしており、複数記事を同時に処理すると、まだキャッシュに書き込まれていない記事同士が互いを見つけられず、本来1つのグループになるべき記事が別グループとして重複登録される競合が起きる
- 前回の実行が（何らかの理由で）まだ終わっていない状態で次のcron起動が重なるケースも考慮し、実行開始時にPostgreSQLのadvisory lock（`pg_try_advisory_lock`）を取得し、取得できなければ即座に終了する（多重起動防止）。これによりDB側での排他制御が完結し、cron側の仕組みに依存しない
- 複数worker並列化はハッカソンのスコープでは不要と判断し、明示的に採用しない

## フロー

### 1. フィード一覧の読み込み
[01-feed-config.md](01-feed-config.md)の`article.json`から`enabled: true`のフィードを全件読み込む。

### 2. RSS取得・記事URL一覧化
各フィードの`url`にGETし、XMLをパースして`<item>`（`title` / `link` / `pubDate`）の一覧を得る。1フィードあたり直近N件（目安：20件）まで。

**鮮度フィルタ**：`pubDate`が現在時刻から**14日**より古い記事は、この時点で候補から除外する（RSSに残っている古い記事を無限に取り込み続けないため。値は固定で決め打ちし、実装者の裁量に委ねない）。`pubDate`が欠損・パース失敗した場合は「新着扱い」として処理を継続する（除外しない。フィード側の不備で記事を取りこぼす方が問題）。

### 3. 新着判定・完全一致URLの扱い
`articles.source_url`に既存レコードがあるURLの場合：
- **本文の再取得はしない**（RSSは同じ記事を何度も一覧に含み続けるため、これを避けるのが目的）
- ただし**タグのマージだけは行う**：今回のフィードの`tags`が既存レコードの`tags`に含まれていなければ、既存レコードの`tags`にUNIONで追加する（同一URLを別フィードが別タグで配信しているケースを取りこぼさないため。「スキップ」ではなく「本文取得だけスキップ」と理解すること）
  - **代表記事への伝播（Codexとの議論で発見した見落とし）**：既存レコードが`is_primary = false`（＝手順6で他のgroupに合流済み）だった場合、そのレコード自身のtagsだけを更新しても、[03-selection.md](03-selection.md)のSELECTは`is_primary = true`の行しか見ないため、追加したタグが選択結果に反映されない。**そのレコードが属する`topic_group_id`の代表記事（`is_primary = true`の行）のtagsにも同じUNIONを反映する**こと
- 完全新着URL（`source_url`が未登録）のみ、手順4以降のフル処理に進む

### 4. 本文取得
新着URLのみ、既存の`internal/providers/fetcher`（jina.ai Reader、`JINA_AI_API_KEY`未設定時はモック）で本文（`Body`）を取得する。取得ロジック自体（`fetchArticle`関数相当）は現行の`jina.go`のものをそのまま流用できる。

**メタデータの優先順位（現行`jina.go`との差分）**：現行の`fetchArticle`はMarkdown本文の`# 見出し`からタイトルを再抽出し、`PublishedAt`を取得時刻、`SourceName`をURLのホスト名から作っている。収集ジョブではこれをやめ、**RSSから得た`title` / `pubDate` / `article.json`の`sourceName`を優先して使う**（jina.aiは本文取得だけに使い、メタデータの抽出には使わない）。RSSの`title`が空の場合のみ、現行ロジック（本文の見出し抽出）にフォールバックする。

**レート制限・エラー処理**：手順4は逐次実行し、1記事の取得に失敗（タイムアウト・非2xx等）してもジョブ全体を止めず、その記事をスキップして次に進む（ログには残す）。`JINA_AI_API_KEY`が未設定の場合はモック記事が返るが、**モック記事はキャッシュへ保存しない**（実在しないダミーURLがDBに蓄積されるのを防ぐため。`cmd/ingest`はモックモードでは「0件保存」で正常終了扱いとする）。

### 5. タグの決定
そのフィードの`article.json`上の`tags`をそのまま記事の初期タグとする（[01-feed-config.md](01-feed-config.md)参照）。タグの表記は[01-feed-config.md](01-feed-config.md)の「タグの正規化」に従うこと（大文字小文字・表記揺れを合わせないと[03-selection.md](03-selection.md)の配列オーバーラップ検索でヒットしなくなる）。

### 6. 重複判定・タグ統合（キャッシュ時点で実施）
新しく取得した記事ごとに、**キャッシュ済みの既存記事のうち`published_at`が直近14日以内のもの**（タグを問わず全件が対象。理由：別タグのフィードが同じニュースを報じるケースを拾うため）に対してタイトル類似度を計算する。

> **Codexとの議論で発見した見落とし**：初稿では「手順2の鮮度フィルタがあるので比較対象は自然に14日以内に収まる」としていたが、これは新規取得記事側の話であり、**既存キャッシュ側は削除ポリシーが無いため時間経過とともに14日を超えた古いgroupが残り続ける**。何もフィルタしないと、新着記事が誤って鮮度切れの古いgroupに合流してしまう。したがって比較クエリ自体に明示的な`published_at >= now() - interval '14 days'`条件を付けること（[03-selection.md](03-selection.md)の候補取得クエリと同じ基準）。

- アルゴリズムは現行`internal/pipeline/dedupe.go`の文字bigram Jaccard類似度（閾値0.35）をそのまま流用する。同じ既知の限界（短い日本語見出しでは意味的に無関係でも高スコアになりうる）も引き継ぐ前提でよい（このドキュメントで新たに解決しようとしない）
- 類似度が閾値以上の既存記事が見つかった場合：
  - 新しい記事は独立した行として保存するが、`topic_group_id`に**見つかった既存記事のtopic_group_id**を設定する（新規groupを作らず既存groupに合流させる）
  - 合流したグループの代表記事（`is_primary = true`）は、本文が最も長いものに更新する（新しい記事の方が長ければ、新しい記事に付け替える。既存のPrimaryだったフラグは下ろす）
  - グループに含まれる全記事のタグを合算し、代表記事の`tags`に反映する（例：Aタグのフィードから来た記事とBタグのフィードから来た記事が同一トピックと判定されたら、代表記事は`tags: [A, B]`になる）
- 見つからなかった場合：新しい`topic_group_id`（自分自身のUUID）を発行し、`is_primary = true`で保存する

### 7. 保存
`articles`テーブルへupsert（[04-schema.md](04-schema.md)）。1トランザクションで新規記事1件＋（合流時は）代表記事の更新を行う。

## 出力
生成パイプライン（[03-selection.md](03-selection.md)）が参照する`articles`テーブルの行。個別の戻り値はない。ただし**最低限の可観測性として、1回の実行ごとに以下をログ出力する**（デモ前にフィードの死活やjina.aiのブロックを発見できるようにするため。監視ダッシュボードや通知の仕組みまでは今回作らない）：
- フィードごとの「RSS取得件数／新着件数／本文取得成功数／本文取得失敗数」
- 実行全体の合計処理時間

## 実行順序についての注意
生成（`demo/generate`・`regenerate`・`batch/run`）は`articles`キャッシュに依存するため、**`cmd/ingest`が最低1回成功していることが前提**になる。運用上：
- 開発環境・デモ準備では、`cmd/ingest`を手動実行してキャッシュを温めてから生成系エンドポイントを叩くこと
- cron運用する場合も、`cmd/ingest`用のcronエントリが`batch/run`用のエントリより十分先行するように間隔をずらす（例：ingestは毎時0分・15分・30分・45分、batch/runはその数分後）

## その他の運用ルール（Codexとの議論を経て追加）
- **Firecrawlフォールバックは今回スコープ外・未実装**：`internal/providers/fetcher/firecrawl.go`は既存するが、位置づけは「RSS一覧取得の代替」ではなく「jina.aiが個別記事の本文取得に失敗した時だけの代替」である。現行の`Fetcher`インターフェースはタグ単位の一括取得を前提にしており、URL単位の本文取得に組み込むには別インターフェースが要る。今回は導入せず、jina.aiの失敗はそのまま手順4の「スキップして継続」で処理する
- **言語判定は行わない**：日本語TTS・日本語台本が前提のため、汎用の言語判定モデルは導入しない。`article.json`に登録するフィードを日本語ニュースサイトに限定する運用ルールで担保する
- **canonical URLの正規化は行わない**：RSSの`<link>`をそのまま`source_url`として扱う（トラッキングパラメータの除去等はしない）。同一記事がクエリ違いで複数行になる可能性はあるが、手順6のタイトル類似度判定で同一`topic_group_id`に合流するため実害は小さいと判断
- **フィード選定時の利用規約確認**：RSSで一覧が公開されていることは、本文をjina.ai経由で取得・保存・TTS要約してよいことを意味しない。`article.json`にフィードを追加する担当者は、対象メディアの利用規約上問題がないことを確認してから追加する（ツールで強制はしない、運用ルールとして明記するのみ）
- **極端に短い本文の除外**：本文取得後、`Body`の文字数が閾値未満（目安：100字）の場合はその記事を保存しない（Cookie同意画面・paywallの断片などをそのまま台本化しないための最低限のガード。専用の品質判定機能は作らない）
