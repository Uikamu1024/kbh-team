# フィード設定ファイル（`article.json`）

**想定パス**: `/backend/config/article.json`（新規。`internal/providers/fetcher`内の`testWhitelist`定数を置き換える）

## 概要
収集対象のRSSフィード一覧と、各フィードが対応するタグ（複数可）を定義する設定ファイル。コード変更・再ビルドなしにフィードの追加/削除/タグ変更ができるようにするのが目的。

## スキーマ（案）
```json
{
  "feeds": [
    {
      "id": "nhk-news-it",
      "url": "https://www.nhk.or.jp/rss/news/cat05.xml",
      "sourceName": "NHKニュース",
      "tags": ["テクノロジー", "AI"],
      "enabled": true
    },
    {
      "id": "itmedia-ai",
      "url": "https://rss.itmedia.co.jp/rss/2.0/aiplus.xml",
      "sourceName": "ITmedia AI+",
      "tags": ["AI"],
      "enabled": true
    }
  ]
}
```

| フィールド | 説明 |
| --- | --- |
| `id` | フィードの一意な識別子（人間が読めるslug。DBの`articles.feed_id`に記録し、障害調査時にどのフィードが原因か追えるようにする） |
| `url` | RSSフィードのURL |
| `sourceName` | 表示用のメディア名（記事のsource_nameに使う。RSSの`<title>`をパースする代わりに明示指定する） |
| `tags` | このフィードが対応するタグの配列。**1フィードが複数タグに属してよい**（例：AIカテゴリのフィードは`["AI", "テクノロジー"]`両方に出す） |
| `enabled` | `false`にすると収集ジョブがこのフィードをスキップする（一時的に壊れたフィードを外す用途） |

## タグの扱いについて（Codexとの議論・ユーザー確認を経て確定）
- タグは**フィード単位で決め打ち**する（記事本文をLLMやEmbeddingで動的分類する方式は採用しない）。タグ名自体もAIに生成させず、常にオンボーディングの固定プリセット一覧から選ぶ。理由：
  - `Requirements.md`に明記されている「記事の選び方：タグ選択式オンボーディング＋カテゴリマッチング」という仕様に合致する
  - ユーザーが選べるタグは元々固定集合（2〜3個までのプリセット）なので、フィード側で対応タグを宣言するだけで十分にカバーできる
  - 記事1件ごとにLLM分類を呼ぶとコスト・レイテンシ・失敗系統が増える割に、この要件（小さく固定のタグ集合）では恩恵が薄い。Embedding分類も同様に、ハッカソンの期間に見合わない準備コスト（閾値調整・評価セット作成）がかかる
  - 「1フィードが複数カテゴリを横断する記事を出す」ケースの取りこぼしより、「関心外の記事が紛れ込む」方が体験を損なうため、広域フィードには安易に複数タグを付けない
- **将来の拡張ポイント（今回は実装しない）**：横断的な記事をどうしても拾いたいフィードが出てきた場合、`article.json`のフィード定義に`includeKeywords`のようなキーワード簡易判定フィールドを追加し、タイトル/RSS descriptionに特定キーワードが含まれる時だけ追加タグを付与する、という拡張は考えられる。ただし今回の設計・実装には含めない
- **カバレッジの目視確認**：フロントの固定タグ一覧それぞれに対して、`enabled: true`のフィードが最低1つ対応していることを、`article.json`を書く際に確認すること（対応表を用意すると分かりやすい）
- 1記事が複数タグを持つケースは、以下の2通りで発生する：
  1. 1つのフィード自体が複数タグに紐付いている場合（上記`tags`配列がそのまま反映される）
  2. 別々のフィード（別タグ）が同じニュースを別々に配信していて、[02-ingestion.md](02-ingestion.md)の重複判定で1つの記事グループに統合された場合（統合時に両方のタグを合算する）

## タグの正規化（Codexレビューを受けて追記）
PostgreSQLの配列オーバーラップ検索（`tags && $1::text[]`、[03-selection.md](03-selection.md)）は文字列の完全一致でしか判定しない。大文字小文字や表記揺れ（`AI`と`ai`、`テクノロジー`と`技術`など）を吸収する仕組みは持たせない。

そのため`article.json`の`tags`は、**フロントエンドのオンボーディングで提示する固定タグ一覧（`users.tags`に書き込まれる文字列）と1文字違わず一致させる**ことを必須ルールとする。表記揺れを許容する正規化ロジック（別名辞書・大文字小文字無視の比較など）は今回設けない。フィード追加時にタグの綴りを間違えると、そのフィードの記事はどのユーザーにも選択されず静かに死ぬ点に注意。

## 読み込みタイミング
収集ジョブ（[02-ingestion.md](02-ingestion.md)）の起動時に毎回読み込む。プロセス常駐させない設計（cronから都度起動するCLI）なので、ホットリロードの仕組みは不要。
